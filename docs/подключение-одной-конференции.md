## Что было не так (корень «каждый в своей конференции»)

1. **webpack-dev проксировал всё на `https://alpha.jitsi.net`** — сигнализация (`/config.js`, `/http-bind`) уходила в чужой публичный кластер, а не в ваш локальный Prosody.
2. **`config.js`** имел `muc: 'conference.meet.jitsi'` (не совпадал с `main_muc = muc.meet.jitsi`) и жёстко прописанный `bosh: '//localhost:5280/http-bind'`.
3. **nginx контейнера вообще не проксировал** `/http-bind`, `/xmpp-websocket`, `/colibri-ws` — браузеру некуда было соединяться.
4. **JwtService** декодировал секрет как Base64, а Prosody (`util.lib.lua`) использует его как **raw-строку** → подпись не сходилась.

## Что ещё мешало войти (вторая серия «граблей» — найдено при проверке входа без камеры)

Отсутствие камеры/микрофона вход не блокирует: клиент продолжает с пустыми треками, а кнопка Join остаётся активной. Вход рвали три реальных дефекта интеграции:

1. **Алгоритм подписи Jitsi-токена.** jjwt сам выбирает самый сильный MAC, который допускает длина ключа, и для этого секрета выдавал `HS384`, а `token_verification` в Prosody проверяет ровно одним алгоритмом — в docker-образах это дефолтный `HS256` (`token/util.lib.lua`: `self.signatureAlgorithm = "HS256"`). Несовпадение видно только в консоли браузера (`Invalid or incorrect alg` → `Authentication failed`), участник просто не попадает в комнату. Теперь `JwtService.signJitsiToken(...)` жёстко закрепляет `Jwts.SIG.HS256`.
2. **Jicofo и JVB не видели Prosody.** Оба контейнера ходят на `XMPP_SERVER=xmpp.meet.jitsi` (`jicofo.conf`: `hostname = "xmpp.meet.jitsi"`), а upstream `docker-jitsi-meet` публикует Prosody под этим сетевым именем. У нас алиаса не было → `UnknownHostException: xmpp.meet.jitsi` в логах Jicofo/JVB, focus-IQ отвечал `service-unavailable`, браузер показывал `conference.connectionError`. В `docker-compose.dev.yml` и `docker-compose.yml` сервису `jitsi-prosody` добавлен сетевой алиас `xmpp.meet.jitsi` (в `jmp-network`) — без него контейнеры видят друг друга только по именам сервисов.
3. **Claim `room` не совпадал с JID-нодой комнаты.** Браузер строит имя MUC через `getBackendSafeRoomName` (`jitsi-meet/react/features/base/util/uri.ts`): decodeURIComponent → NFKC → lowercase → encodeURIComponent → lowercase — то есть `тестовая-комната` → `%d1%82%d0%b5%d1%81%d1%82%d0%be%d0%b2%d0%b0%d1%8f-%d0%ba%d0%be%d0%bc%d0%bd%d0%b0%d1%82%d0%b0`. `verify_room` в Prosody сравнивает с этой нодой claim из токена (в нижнем регистре) и при несовпадении возвращает `room-mismatch` → браузер рвёт вход с «Room does not match the room from token». В токене же лежало человекочитаемое имя. Теперь `generateJitsiToken`/`generateGuestToken` кладут в claim результат `Conference.backendSafeRoomName(...)`; в URL ссылки имя осталось человекочитаемым — клиент кодирует его сам.

**Проверено end-to-end** (машина без камеры): ссылка получена через `GET /api/v1/join/{slug}` (`decision: REDIRECT`), в токене `"alg":"HS256"` и `"room":"%d1%82…"`; браузер — `APP.conference.isJoined() = true`, участник «Тест» с бейджем Moderator, комната «Тестовая Комната»; Prosody — `Authenticated as …@meet.jitsi` и metadata для `%d1%82…@muc.meet.jitsi`, Jicofo — `Joining %d1%82…@muc.meet.jitsi`. Отсутствие камеры даёт только предупреждение `gum.not_found` на prejoin и входу не мешает.

## Как устроено решение (один образ, два контура)

По образцу официального `jitsi/web`: разница контуров инжектируется **из переменных окружения при старте контейнера**, код не правится.

- `jitsi-meet/docker/55-jmp-config.sh` — скрипт в `/docker-entrypoint.d/`, перезаписывает по уникальным ключам `config.js` (domain/muc/disableP2P/stunServers) и `nginx.conf` (`set $jmp_prosody/$jmp_jvb/$subdir`). Идемпотентен, в конце делает `nginx -t`.
- `config.js` — `bosh`/`websocket` теперь строятся из `location` + `subdir`, потому что один бандл работает и на `http://localhost:8085`, и на `https://meet.slamx.ru`.
- `nginx.conf` — SSI + `resolver 127.0.0.11` + переменные в `proxy_pass` (стартует без Prosody, переживает рестарт бэкендов). `subdir` при пустом префиксе = `/` (иначе склеилось бы `//hosthttp-bind`).
- `webpack.config.js` — dev-прокси теперь на `http://localhost:8085` (ваш контейнер), `ws:true`, хост через `WEBPACK_DEV_SERVER_HOST`.
- `JwtService` — `app-secret-type: raw|base64` (по умолчанию `raw` = совместимость с Prosody); подпись Jitsi-токенов закреплена на `HS256`, claim `room` — backend-safe имя (`Conference.backendSafeRoomName`).
- compose — у `jitsi-prosody` сетевой алиас `xmpp.meet.jitsi`, по которому Jicofo/JVB находят XMPP.
- `Conference`/`ConferenceService` — нормализация `roomName` (trim→lower, пробелы→`-`) под `verify_room` Prosody; `Conference.backendSafeRoomName` переводит имя в percent-encoded lowercase форму JID-ноды.
- Удалил `config (для прода нужно использовать его).js` — это был upstream-шаблон с заглушками `example.com`, который возвращал бы баг жёстко прописанных хостов (в git, восстанавливается).

## Как переключить локальный контур на прод — чеклист

**Локальный контур (сейчас):**
```bash
docker compose -f docker-compose.dev.yml up -d --build jitsi-web   # nginx на :8085
# backend: профиль dev (app-secret-type=raw); при необходимости рестарт
WEBPACK_DEV_SERVER_HOST=0.0.0.0 make dev                           # доступ со 2-й машины
```
В `.env` для локального: `JITSI_DOMAIN=localhost:8000`, `JITSI_SCHEME=http`, `JMP_PUBLIC_URL=http://localhost:5173`.

**Прод (потом):** меняете только `.env` + поднимаете `docker-compose.yml` — код/образ те же:
```
JITSI_DOMAIN=meet.slamx.ru   JITSI_SCHEME=https   JMP_PUBLIC_URL=https://a.slamx.ru
JITSI_JWT_APP_SECRET_TYPE=raw
XMPP_MUC_DOMAIN=muc.meet.jitsi
DISABLE_P2P=true
```
`docker compose up -d --build jitsi-web`. Всё, что отличается (адреса Prosody/JVB, домен, префикс), читается из env в `docker-compose.yml` → генератор подставит в контейнере.

**Замечание:** перестроение контейнеров и рестарт бэкенда ещё не выполнялись — чтобы фик заработал, нужно `docker compose -f docker-compose.dev.yml up -d --build jitsi-web` + `make dev` + рестарт Java-процесса (подхватит `app-secret-type=raw` и нормализацию имён).

## Третья серия «граблей» — кнопка «Начать» в карточке комнаты (найдено при разборе жалобы «вход не происходит»)

Симптом: после нажатия «Начать» на карточке конференции вход не происходил. Разбор показал, что токен и серверная цепочка были в порядке (токен из консоли пользователя валиден, его клиент до XMPP вообще не доходил; ложные следы «Invalid signature» — артефакт усечённого тестового URL). Реальными блокерами были три дефекта:

1. **`.env` мешал dev-контуру.** В `JITSI_DOMAIN` стоял прод-адрес `a.slamx.ru/jitsi`, а `JITSI_SCHEME` не был задан. Кнопка «Начать» открывала ссылку на недоступный из локальной сети хост (в консоли — `http://a.slamx.ru/jitsi/...`). Для локального контура в `.env` зафиксировано `JITSI_DOMAIN=localhost:8000` и `JITSI_SCHEME=http` (прод-значения — в комментарии рядом). Это ровно тот «один переключатель», который описан выше.
2. **Prejoin-экран требовал второго клика.** Ссылки из кабинета вели на страницу предпросмотра камеры — вход завершался только после нажатия «Join meeting», что выглядело как «вход не происходит». `JitsiLinkBuilder.roomUrl(...)` теперь добавляет хэш `#config.prejoinConfig.enabled=false` (ключ есть в `configWhitelist.ts`, в dev-режиме whitelisting вообще отключён) — из кабинета участник попадает в конференцию сразу. Хэш добавляется последним: JWT обязан остаться в query, иначе `parseJWTFromURLParams` его не найдёт.
3. **Повторный вход в ACTIVE-конференцию был заблокирован.** «Начать» на карточке был `disabled` для статуса ACTIVE, а сам `startConference` для ACTIVE бросает `Conference can only be started from scheduled or ended state`. То есть в уже идущую комнату из кабинета войти было нельзя. `ConferencesPage.handleStart(id, status)` теперь для ACTIVE пропускает вызов `start` и только запрашивает персональную ссылку (`POST /conferences/{id}/token`) и открывает её; кнопка всегда активна и для ACTIVE подписана «Присоединиться» (в списке — аналогично).

**Проверено end-to-end через реальный UI:** карточка ACTIVE показывает «Присоединиться» (enabled) → клик выполняет только `generateToken` (200) + `window.open(roomUrl)`, без `startConference`; ссылка вида `http://localhost:8000/<room>?jwt=...#config.prejoinConfig.enabled=false` приводит к немедленному auto-join: `APP.conference.isJoined() = true`, роль moderator, prejoin-экран отсутствует, в консоли нет `authfail`/`Invalid signature`/`token required`; конференция осталась ACTIVE, ничего не перезапускалось.

**Замечание для будущих проверок:** при ручном копировании ссылки с JWT всегда копируйте её целиком — усечённый токен в логах Prosody выглядит как `Invalid signature`, что уводит от реальной причины.
