## Что было не так (корень «каждый в своей конференции»)

1. **webpack-dev проксировал всё на `https://alpha.jitsi.net`** — сигнализация (`/config.js`, `/http-bind`) уходила в чужой публичный кластер, а не в ваш локальный Prosody.

4. **JwtService** декодировал секрет как Base64, а Prosody (`util.lib.lua`) использует его как **raw-строку** → подпись не сходилась.

## Что ещё мешало войти (вторая серия «граблей» — найдено при проверке входа без камеры)

Отсутствие камеры/микрофона вход не блокирует: клиент продолжает с пустыми треками, а кнопка Join остаётся активной. Вход рвали три реальных дефекта интеграции:

1. **Алгоритм подписи Jitsi-токена.** jjwt сам выбирает самый сильный MAC, который допускает длина ключа, и для этого секрета выдавал `HS384`, а `token_verification` в Prosody проверяет ровно одним алгоритмом — в docker-образах это дефолтный `HS256` (`token/util.lib.lua`: `self.signatureAlgorithm = "HS256"`). Несовпадение видно только в консоли браузера (`Invalid or incorrect alg` → `Authentication failed`), участник просто не попадает в комнату. Теперь `JwtService.signJitsiToken(...)` жёстко закрепляет `Jwts.SIG.HS256`.
2. **Jicofo и JVB не видели Prosody.** Оба контейнера ходят на `XMPP_SERVER=xmpp.meet.jitsi` (`jicofo.conf`: `hostname = "xmpp.meet.jitsi"`), а upstream `docker-jitsi-meet` публикует Prosody под этим сетевым именем. У нас алиаса не было → `UnknownHostException: xmpp.meet.jitsi` в логах Jicofo/JVB, focus-IQ отвечал `service-unavailable`, браузер показывал `conference.connectionError`. В `docker-compose.dev.yml` и `docker-compose.yml` сервису `jitsi-prosody` добавлен сетевой алиас `xmpp.meet.jitsi` (в `jmp-network`) — без него контейнеры видят друг друга только по именам сервисов.
3. **Claim `room` не совпадал с JID-нодой комнаты.** Браузер строит имя MUC через `getBackendSafeRoomName` (`jitsi-meet/react/features/base/util/uri.ts`): decodeURIComponent → NFKC → lowercase → encodeURIComponent → lowercase — то есть `тестовая-комната` → `%d1%82%d0%b5%d1%81%d1%82%d0%be%d0%b2%d0%b0%d1%8f-%d0%ba%d0%be%d0%bc%d0%bd%d0%b0%d1%82%d0%b0`. `verify_room` в Prosody сравнивает с этой нодой claim из токена (в нижнем регистре) и при несовпадении возвращает `room-mismatch` → браузер рвёт вход с «Room does not match the room from token». В токене же лежало человекочитаемое имя. Теперь `generateJitsiToken`/`generateGuestToken` кладут в claim результат `Conference.backendSafeRoomName(...)`; в URL ссылки имя осталось человекочитаемым — клиент кодирует его сам.

**Проверено end-to-end** (машина без камеры): ссылка получена через `GET /api/v1/join/{slug}` (`decision: REDIRECT`), в токене `"alg":"HS256"` и `"room":"%d1%82…"`; браузер — `APP.conference.isJoined() = true`, участник «Тест» с бейджем Moderator, комната «Тестовая Комната»; Prosody — `Authenticated as …@meet.jitsi` и metadata для `%d1%82…@muc.meet.jitsi`, Jicofo — `Joining %d1%82…@muc.meet.jitsi`. Отсутствие камеры даёт только предупреждение `gum.not_found` на prejoin и входу не мешает.

## Как устроено решение (один образ, два контура)

По образцу официального `jitsi/web`: разница контуров инжектируется **из переменных окружения при старте контейнера**, код не правится.

- `jitsi-meet/docker/55-jmp-config.sh` — скрипт в `/docker-entrypoint.d/`, перезаписывает по уникальным ключам `config.js` (domain/muc/disableP2P/stunServers/leaveRedirectUrl), `nginx.conf` (`set $jmp_prosody/$jmp_jvb/$subdir`), а с переездом на префикс — ещё `base.html` (`<base href>`) и `manifest.json` (`start_url`/`scope`). Идемпотентен, в конце делает `nginx -t`.
- `config.js` — `bosh`/`websocket` теперь строятся из `location` + `subdir`, потому что один бандл работает и на `http://localhost:8000`, и на `https://a.slamx.ru/meet-legacy/`.
- `nginx.conf` — SSI + `resolver 127.0.0.11` + переменные в `proxy_pass` (стартует без Prosody, переживает рестарт бэкендов). `subdir` при пустом префиксе = `/` (иначе склеилось бы `//hosthttp-bind`).
- `webpack.config.js` — dev-прокси теперь на `http://localhost:8085` (ваш контейнер), `ws:true`, хост через `WEBPACK_DEV_SERVER_HOST`.
- `JwtService` — `app-secret-type: raw|base64` (по умолчанию `raw` = совместимость с Prosody); подпись Jitsi-токенов закреплена на `HS256`, claim `room` — backend-safe имя (`Conference.backendSafeRoomName`).
- compose — у `jitsi-prosody` сетевой алиас `xmpp.meet.jitsi`, по которому Jicofo/JVB находят XMPP.
- `Conference`/`ConferenceService` — нормализация `roomName` (trim→lower, пробелы→`-`) под `verify_room` Prosody; `Conference.backendSafeRoomName` переводит имя в percent-encoded lowercase форму JID-ноды.
- Удалил `config (для прода нужно использовать его).js` — это был upstream-шаблон с заглушками `example.com`, который возвращал бы баг жёстко прописанных хостов (в git, восстанавливается).

## Третья серия «граблей» — кнопка «Начать» в карточке комнаты (найдено при разборе жалобы «вход не происходит»)

Симптом: после нажатия «Начать» на карточке конференции вход не происходил. Разбор показал, что токен и серверная цепочка были в порядке (токен из консоли пользователя валиден, его клиент до XMPP вообще не доходил; ложные следы «Invalid signature» — артефакт усечённого тестового URL). Реальными блокерами были три дефекта:

1. **`.env` мешал dev-контуру.** В `JITSI_DOMAIN` стоял прод-адрес `a.slamx.ru/jitsi`, а `JITSI_SCHEME` не был задан. Кнопка «Начать» открывала ссылку на недоступный из локальной сети хост (в консоли — `http://a.slamx.ru/jitsi/...`). Для локального контура в `.env` зафиксировано `JITSI_DOMAIN=localhost:8000` и `JITSI_SCHEME=http` (прод-значения — в комментарии рядом). Это ровно тот «один переключатель», который описан выше.
2. **Prejoin-экран требовал второго клика.** Ссылки из кабинета вели на страницу предпросмотра камеры — вход завершался только после нажатия «Join meeting», что выглядело как «вход не происходит». `JitsiLinkBuilder.roomUrl(...)` теперь добавляет хэш `#config.prejoinConfig.enabled=false` (ключ есть в `configWhitelist.ts`, в dev-режиме whitelisting вообще отключён) — из кабинета участник попадает в конференцию сразу. Хэш добавляется последним: JWT обязан остаться в query, иначе `parseJWTFromURLParams` его не найдёт.
3. **Повторный вход в ACTIVE-конференцию был заблокирован.** «Начать» на карточке был `disabled` для статуса ACTIVE, а сам `startConference` для ACTIVE бросает `Conference can only be started from scheduled or ended state`. То есть в уже идущую комнату из кабинета войти было нельзя. `ConferencesPage.handleStart(id, status)` теперь для ACTIVE пропускает вызов `start` и только запрашивает персональную ссылку (`POST /conferences/{id}/token`) и открывает её; кнопка всегда активна и для ACTIVE подписана «Присоединиться» (в списке — аналогично).

**Проверено end-to-end через реальный UI:** карточка ACTIVE показывает «Присоединиться» (enabled) → клик выполняет только `generateToken` (200) + `window.open(roomUrl)`, без `startConference`; ссылка вида `http://localhost:8000/<room>?jwt=...#config.prejoinConfig.enabled=false` приводит к немедленному auto-join: `APP.conference.isJoined() = true`, роль moderator, prejoin-экран отсутствует, в консоли нет `authfail`/`Invalid signature`/`token required`; конференция осталась ACTIVE, ничего не перезапускалось.

**Замечание для будущих проверок:** при ручном копировании ссылки с JWT всегда копируйте её целиком — усечённый токен в логах Prosody выглядит как `Invalid signature`, что уводит от реальной причины.

## Переезд Jitsi на `https://a.slamx.ru/meet-legacy/` (24.09.2026)

Раньше веб Jitsi отдавался с корня отдельного хоста `https://meet.slamx.ru`. Теперь он живёт на пути `/meet-legacy` общего хоста платформы, а `meet.slamx.ru` из `nginx-proxy.conf` убран совсем.

### Схема: префикс существует только для браузера

Внешний nginx срезает `/meet-legacy` (`proxy_pass http://jitsi/;` — слэш на `proxy_pass` **без переменной**, иначе срезание молча не применяется), поэтому контейнер как раздавал приложение со своего корня, так и раздаёт: его `location = /http-bind`, `try_files` и кэш-регулярки не правились. Клиенту путь возвращается через три значения, которые генерит `55-jmp-config.sh` из `APP_PREFIX`:

1. `var subdir = '/meet-legacy/';` в `config.js` → `bosh`/`websocket` (`'//' + location.host + subdir + 'http-bind'`). Подставляется на старте контейнера: энтрипойнт правит строку по ключу, идемпотентно. `set $subdir` в `nginx.conf` остался только fallback-значением для SSI — на request-time SSI для этой строки полагаться нельзя (см. «Инцидент» в конце).
2. `<base href="/meet-legacy/" />` в `base.html` — ключевое. Без него относительные ссылки приложения (`css/all.css`, `libs/*.js`, `lang/*.json`, `sounds/*`, `images/watermark.svg`) уходят в корень `a.slamx.ru`, там их перехватывает SPA-фолбэк `jmp-ui` и отвечает **200 + `text/html`**: скрипт не грузится, но ошибки загрузки нет, и `index.html` не показывает свой экран ретрая. Один файл закрывает и `static/*.html` (close, offline, dialInInfo), которые подключают его через SSI.
3. `start_url`/`scope` в `manifest.json` — иначе PWA-ярлык устанавливается на весь хост и открывает кабинет. Самого файла в образе не было: `jitsi-meet/Dockerfile` копировал `*.html` и `*.js`, но не `manifest.json`, поэтому добавлен отдельный `COPY`. На всякий случай этот шаг не фатален при отсутствии файла (скрипт-энтрипойнт базового образа с `exit 1` не даёт контейнеру стартовать, а терять здесь нечего, кроме иконки на домашнем экране) — в отличие от `base.html`, который в образе есть и остаётся обязательным.

Отдельно `location = /meet-legacy { return 302 /meet-legacy/$is_args$args; }`: у пути без слэша на конце нет второго `/`, `contextRoot()`/`getLocationContextRoot()` берут корень хоста, и service worker зарегистрировался бы на `/` — после этого он начал бы обслуживать запросы платформы.

### Что не поддается префиксу

`/colibri-ws/` оставлен **в корне** `a.slamx.ru`: JVB объявляет абсолютный `wss://$JVB_WS_DOMAIN/colibri-ws/<id>/…`, а lib-jitsi-meet берёт этот URL дословно (фильтр `bridgeChannel.ignoreDomain` в `config.js` не включён), так что путь в него не вставишь. Отсюда `JVB_WS_DOMAIN: a.slamx.ru` вместо домена.

### Известные ограничения (приняты осознанно)

- **Общий origin → общий `localStorage`.** И платформа, и Jitsi пишут язык в ключ `i18nextLng` (`jmp-ui/src/i18n/config.ts`, `jitsi-meet/react/features/base/i18n/i18next.ts`): язык, выбранный на prejoin, становится языком кабинета, и наоборот. Лечится явным `cacheName` с одной из сторон.
- **`meet.slamx.ru` больше не слушается.** Старые закладки и сохранённые адреса комнат дают несовпадение имени сертификата (запрос падает на первый 443-server), certbot для этого имени сертификат не выпрашивает.
- **Имя комнаты = последний сегмент пути**, поэтому комната `meet-legacy` живёт по `/meet-legacy/meet-legacy` и работает; префикс при этом распознаётся клиентом как «тенант» (`uri.ts:parseURIString`), но здесь это ни на что не влияет: `tokenRespectTenant` не включён, в MUC-JID и в claim `room` попадает только комната. Правило на будущее: префикс не должен начинаться/заканчиваться на `-` и быть длиннее 63 символов — тогда клиент начнёт показывать `invalidTenant`.
- Имена комнат, совпадающие с путями сигналинга и статики (`http-bind`, `xmpp-websocket`, `config.js`, `static`, `sounds`, …), неработоспособны — как и в корневой схеме раньше.
- **Ручной ввод кода комнаты в кабинете (`jmp-ui`) не переехал.** `HomePage.tsx:57` берёт базу из `VITE_JITSI_URL`, а иначе — литерал `http://localhost:8000`; `jmp-ui/Dockerfile` не принимает build-arg, так что в образе прод-кабинета остаётся локальный адрес (дефект был и до переезда, ссылкой из `/j/<slug>` не проявляется). Лечится либо `ARG`+`build.args` для `VITE_JITSI_URL`, либо фолбэком на тот же origin: `${window.location.origin}/meet-legacy`.

### Порядок выкатки и откат

1. **Сначала образ** (`docker build -t vostrlog/jmp-jitsi-meet ./jitsi-meet && docker push`), только потом env: иначе `APP_PREFIX=/meet-legacy` поставит `$subdir`, а `<base href>` останется `/` — «подключается, но страница покорёжена».
2. На проде: `docker compose pull jitsi-meet`, затем `docker compose up -d` (смена `environment:` пересоздаёт контейнеры), Flyway применит `V6__retire_meet_subdomain_in_tenants.sql`.
3. `nginx-proxy.conf` — в последнюю очередь. Файл смонтирован `:ro`, а `git pull` заменяет inode, поэтому контейнер может продолжать читать старые байты: проверять `docker exec nginx-proxy grep -c 'location ^~ /meet-legacy/' /etc/nginx/user_conf.d/nginx-proxy.conf`, затем `nginx -t && nginx -s reload`. `upstream`-ы резолвятся на старте nginx — после пересоздания контейнеров нужен ещё один reload.
4. Откат обратный: `APP_PREFIX=""`, `JITSI_DOMAIN=meet.slamx.ru`, вернуть блок `server_name meet.slamx.ru`. При пустом `APP_PREFIX` скрипт возвращает `base.html`/`manifest.json`/`$subdir` к исходным байтам, так что пересборка образа для отката не нужна.

## Инцидент при выкатке на прод: `subdir` не доехал до клиента (24.09.2026)

Симптом: вход в конференцию падал ещё до XMPP — консоль показывала `WebSocket connection failed` на `wss://a.slamx.ru/xmpp-websocket?...` (корень хоста, без префикса), затем `Strophe connfail` и оверлей перезагрузки. Контрольный `GET https://a.slamx.ru/xmpp-websocket` возвращал HTML кабинета: апгрейд до `101` отдавать было некому — запрос перехватывал SPA-фолбэк платформы.

Причина: `config.js` доезжал до браузера с **нераскрытым** SSI-плейсхолдером (`var subdir = '<!--# echo var="subdir" default="/" -->';`), а фолбэк в `config.js` при нераскрытой директиве молча ставит `subdir = '/'`. SSI-фильтр обрабатывает ответ только тех MIME-типов, что перечислены в `ssi_types` (по умолчанию — только `text/html`), а `config.js` — JS: без `ssi_types application/javascript` подключаемый в `index.html` файл оставался с плейсхолдером. В итоге `bosh`/`websocket` собирались в корне общего хоста.

Исправление: подстановка префикса больше не зависит от request-time SSI — `55-jmp-config.sh` правит `var subdir` на старте контейнера, как и остальные контурные значения; `ssi_types application/javascript` в `nginx.conf` оставлен страховкой. Требуется пересборка образа (правка в энтрипойнте). Диагностика на будущее: `curl -s https://a.slamx.ru/meet-legacy/config.js | grep "var subdir"` должен показывать литеральный префикс (`var subdir = '/meet-legacy/';`); если в браузере уже закэширован сломанный файл — жёсткая перезагрузка (Ctrl+Shift+R).
